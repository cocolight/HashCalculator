## 项目定位与边界

- **是**：一个轻量、跨平台的哈希计算器，核心是「算一个文件的 MD5/SHA-256 并核对」；批量页把同一件事扩展到「一次算一批文件」。
- **不是**：哈希算法套件、流水线/脚本化工具、CLI-first 工具。
- **取舍准则**：任何显著增加体积、依赖或交互复杂度的功能，须先证明其收益大于定位稀释的成本。

| 能力 | 说明 |
| ---- | ---- |
| 算法 | MD5 + SHA-256（RustCrypto），后台线程计算 |
| 读取 | `memmap2` 内存映射，大文件不整体载入 |

## 主题一：正确性与回归保障【最高优先】

> 判断依据：上一轮把计算路径从顺序改为并发，这是最易引入难复现缺陷的改动；而项目没有任何自动化测试。**先把地基建起来，再谈功能。**

### P2 · 自动化测试

| 项 | 内容 |
| -- | ---- |
| 目标 | 让哈希正确性可被自动回归，覆盖并发计算路径与批量路径 |
| 价值 | 高——锁住已完成的 1.6x 成果，为后续所有改动提供安全网 |
| 成本 | M |
| 风险 | 低 |
| 依赖 | 无（P3 依赖本项） |
| 现状 | **部分具备**：`worker` 与 `batch` 模块内已有单元测试（已知向量、空文件、批量与单文件路径互证、取消、CSV 转义），因本仓库是**纯 binary crate**，测试须写在模块内而非 `tests/` |
| 验收 | ① 补齐**边界尺寸**（恰好一块 / 一块+1B / 非对齐）与更多已知向量；② 覆盖目录非递归、去重、失败继续等批量行为；③ `cargo test` 全绿且成为 CI 的一环 |

### P1 · 空文件按标准计算【已完成】

0.4.2（PR #5）已落地：0 字节文件输出 MD5 `d41d8cd98f00b204e9800998ecf8427e`、SHA-256 `e3b0c442…2b855`。
`memmap2 0.9.11` 在 Windows 后端对 0 长度文件不调用 `CreateFileMappingW`，因此无需特判分支。

> **验证提示**：`certutil -hashfile` 对 0 字节文件直接报 `0x800703ee ERROR_FILE_INVALID`，**不能**用作空文件基准；
> 改用 Python `hashlib` 与 PowerShell `Get-FileHash` 两套独立实现互证。

## 主题六：产品形态

### P11 · 多文件 / 批量【已完成】

0.4.2（PR #7）已落地「批量」标签页：多选文件 + 选文件夹（**非递归**）→ **顺序**计算 → 虚拟化表格 → 导出 CSV/TXT、复制选中。单文件页行为不变。

实施中的关键取舍：

- **顺序而非并发**：单个文件内部已用双线程并行 MD5/SHA-256；若再对 N 个文件并发，会变成 2N 个线程争抢 CPU 与页缓存，进度与取消语义急剧复杂化，收益却有限。
- **复用而非镜像**：批量直接调用 `worker::hash_file`（PR #6 抽出），不写第二套会与生产路径漂移的实现。
- **零新增依赖**：表格用 `Grid` + `ScrollArea::show_rows` 虚拟化；文件夹只读一层，手写 `read_dir` 即可，无需 `walkdir`。
- **同批不中断**：单个文件失败只标记该行，继续处理后续文件；取消后已完成行的结果保留，其余可再次「开始」续算。

明确不做：拖拽加入批量（P4 另议）、目录递归（需引入 `walkdir` 并处理符号链接环）、多文件并发、断点续传、结果历史。

## 不做清单

| 项 | 理由 |
| -- | ---- |
| 继续榨取单流 MD5（SIMD / 多缓冲 / 跨块并行） | 单文件是 Merkle–Damgård 链，块间强依赖，**物理上不可按块并行**；MD5 在 x86 无硬件后端。已在 [perf-plan.md](perf-plan.md) 论证并排除 |
| 用非 RustCrypto 的自研哈希实现提速 | 无必要，且引入正确性风险；相对成熟实现收益不成比例 |
| 引入重型 GUI/Web 框架重构界面 | 与「轻量」定位不符，成本远大于收益 |
| 继续扩张批量能力（目录递归 / 并发 / 队列持久化） | 已落地的批量页覆盖了真实场景；再往上走会稀释定位，且与 P6 的健壮性投入冲突 |
| 为「功能齐全」而堆砌算法 | 应以真实场景（校验下载文件）为准，而非数量 |
