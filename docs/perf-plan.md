# HashCalculator 大文件性能优化方案

**项目**：`e:\Project\HashCalculator`（Rust + egui）
**状态**：核心优化已完成并验证（v0.4.1 → v0.4.3）
**目标**：降低 GB 级文件计算耗时，且哈希结果与系统工具逐位一致

> 本文档已按实测数据修订。原稿中若干技术断言经第一手核验后被证伪，见「关键事实核验」。

---

## 结论速览

| 文件 | 优化前 | 优化后 | 提升 |
| ---- | ------ | ------ | ---- |
| 20MB | 54 ms  | 34 ms  | 1.59x |
| 1GB  | 2742 ms | 1709 ms | 1.60x |
| 4GB  | 11123 ms | 6847 ms | 1.62x |

- 收益来源：**MD5 与 SHA-256 双线程并行**（各占一核）。
- 正确性：上述文件及 1B / 100B / 7777777B / 不足 4MB 等非对齐文件，MD5/SHA-256 均与 `certutil` **逐位一致**。
- **天花板**：单文件哈希是顺序依赖的（Merkle–Damgård），MD5 在 x86 无硬件加速，是吞吐地板（本机实测约 598 MB/s）。因此**不存在「总耗时降到 1/3~1/5」的路径**。

## 验收标准

| 项     | 标准                                                         |
| ------ | ------------------------------------------------------------ |
| 正确性 | MD5/SHA-256 与 `certutil -hashfile <文件> MD5` / `SHA256` 完全一致 |
| 边界   | 非 4MB 对齐、极小文件（1B）也必须一致                        |
| 小文件 | <100MB 文件耗时**不得劣化**                                  |
| 大文件 | 4GB+ 不卡顿、取消可用、内存占用不随文件增大                  |

## 关键事实核验（原稿中被证伪的断言）

| 原稿断言 | 事实 | 依据 |
| -------- | ---- | ---- |
| 给 md-5/sha2 加 `features = ["asm"]`，SHA-256 快 3~6 倍 | **feature 不存在，照写会构建失败** | `sha2-0.11.0`、`md-5-0.11.0` 的 Cargo.toml features 仅 `alloc/oid/zeroize` |
| 需要开 feature 才有 SHA-NI 加速 | **SHA-NI 已默认运行时启用** | `sha2-0.11.0/src/sha256.rs` 默认分支用 `cpufeatures::new!(shani_cpuid, "sha", …)` + `if shani_cpuid::get()` |
| 「MD5 快 2~3 倍」 | **不可能** | `md-5-0.11.0/src/compress.rs` 仅有 `loongarch64_asm`，x86 无任何硬件后端 |
| 用 `Digest::midstate()` 做块级并行 | **API 不存在，且概念不成立** | `digest-0.11.3` 无该符号；单流哈希块 N 依赖块 N-1，无法分块并行 |
| 删 worker 的 `request_repaint()` 因「egui 非线程安全」 | 理由错误，**仅属去冗余** | `egui-0.36.2/src/context.rs` 明确支持跨线程 `request_repaint` |

## 已实施阶段

### 阶段 0 · 基线测量

- tag：`v0.4.1-baseline`
- 新增无界面入口 `hash_calculator --bench <path>`：复用与 GUI **完全相同**的 worker 计算路径，输出 `md5 / sha256 / elapsed_ms / throughput`，供跨阶段对比与 `certutil` 交叉验证。
- 基准文件：20MB / 1GB（随机）、4GB（全零；哈希与数据内容无关）。
- **环境**：AMD Ryzen 7 5700X（8C/16T，Zen 3），CPU 特性含 `sha-ni,avx2,sse4.2`。
- **独立交叉验证**：另有一套直接测量单算法的独立基准给出 1 GiB 下 MD5 597.3 MiB/s、SHA-256 1693.9 MiB/s，与本方案的推算吻合。

### 阶段 1 · worker 解耦 egui + 进度节流

- tag：`v0.4.2-ui`
- worker 不再持有 `egui::Context`：UI 侧计算期间每帧 `request_repaint()` 已保证刷新，worker 的调用只是冗余；解耦后计算路径可脱离 GUI 运行（`--bench` 的前提）。
- 进度由「每 256MB 一次」改为「**每 100ms** 一次」，大文件进度更连续；处理粒度 64MB → 4MB，取消响应更快。
- 验证：哈希与基线逐位一致，吞吐无劣化。

### 阶段 2 · MD5 ∥ SHA-256 双线程并行（核心收益）

- tag：`v0.4.3-parallel`
- `std::thread::scope` 起两线程，各自**零拷贝**遍历同一份 `&mmap`（无 channel 传块、无 memcpy），总耗时 ≈ `max(MD5, SHA-256)`。
- 协调线程取两者已完成字节数的**较小值**作为整体进度（慢者决定完工），按 100ms 节流上报；取消按 4MB 块粒度检查。
- **踩坑记录**：协调线程首版用 100ms 轮询，使 20MB 从 54ms 退化到 101ms —— 轮询间隔成了小文件的完工延迟。改为 2ms 轮询（远小于进度节流）后恢复正常。

### 数据互证：为什么是 1.60x 而不是 1.35x

| 分量（1 GiB，一次性） | 耗时 | 来源 |
| ---- | ---- | ---- |
| MD5 纯计算 | 1.714 s | 独立基准（warm mmap，3 次取中位） |
| SHA-256 纯计算 | 0.605 s | 同上（SHA-NI 生效，1693.9 MiB/s） |
| mmap 缺页 | ~0.42 s | 独立实测 ≈0.37 s/GiB |
| **串行一次性合计** | **2.742 s** | 本方案基线（≈ 1.714 + 0.605 + 0.42） |
| **并行一次性** | **1.714 s** | 本方案实测（= max(MD5, SHA)） |

- 并行实测 **1714 ms 恰好等于 MD5 单独纯计算 1.714 s** → MD5 是新的地板，且 **mmap 缺页成本已被掩盖**：SHA-256 线程跑得比 MD5 快，会先行把页预取，MD5 线程不再支付缺页成本。
- 若用「热缓存稳态」作分母（2.315 s / 1.714 s = 1.35x）会低估真实收益；App 每次都是新映射（一次性），正确比值是 **2742 / 1714 = 1.60x**。

## 未采纳 / 已排除

| 项 | 结论 | 原因 |
| -- | ---- | ---- |
| I/O 改造：`mmap` → 流式读取 | **不做**（收益已被并行吸收） | mmap 缺页成本确实存在（独立实测 ≈0.37 s/GiB），但双线程下更快的 SHA-256 线程会先行预取这些页，MD5 线程不再支付缺页成本；实测 1 GiB 并行耗时恰等于 MD5 单独纯计算耗时，见「数据互证」。改流式只剩引入短读正确性风险 |
| N 线程块级并行 | **不可行** | 单流 Merkle–Damgård 链块间强依赖，无法按块并行 |
| 为 MD5 引入 SIMD/多缓冲 | **暂不做** | 多缓冲只能并行**多条独立消息**，对单文件单流无效 |

## 三条硬纪律（回顾）

1. **改动面从小到大**：配置 → UI → 计算路径 → 并发。
2. **并行永远最后**：并发问题难复现，前面保持确定性代码以便二分定位。
3. **删旧代码单独一个 commit**：与「改新逻辑」分开，出问题时能区分是改坏还是删坏。
